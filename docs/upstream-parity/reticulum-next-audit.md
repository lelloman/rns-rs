## Audit Vocabulary

- **Needs port**: compatible behavior is absent or observably different.
- **Needs coordinated port**: related changes must be implemented together.
- **Needs decision**: architecture differs and the compatibility surface must
  be chosen explicitly.
- **Integrated**: applicable behavior is implemented with recorded evidence.
- **Structurally covered**: the Rust design already provides the behavior or
  avoids the upstream failure through a different invariant.
- **Documentation follow-up**: native documentation is required after the
  related behavior exists.
- **Deferred**: applicable work is deliberately postponed with rationale and
  impact recorded.
- **Non-runtime**: metadata, changelog, generated artifacts, or upstream-only
  tests require no independent Rust runtime change.

## Per-Commit Analysis

### 1. `2c7cf827` — Future workblock generation

**Upstream change:** `stamp_workblock` now delegates to `_stamp_workblock`,
which builds the same bytes as before (only the buffer type changes). A new
`_stamp_workblock_future` adds a memory-hard expansion: every round derives
its chunk from a rolling HKDF state plus eight 64-byte probes taken from
pseudo-random positions of the workblock built so far, so the whole block has
to be kept in memory while it is built. The comment typo fix is cosmetic.

**Rust applicability:** No upstream code calls `_stamp_workblock_future`;
every stamp, discovery, path request and keystamp workblock still comes from
the unchanged algorithm, which `rns_core::stamp::stamp_workblock` matches.
There is nothing to interoperate with until upstream uses it.

**Local handling and evidence:** None now. When upstream switches a stamp
type to the new expansion, port it into `rns-core` with byte vectors
generated by the Python function, and switch the same stamp types.

**Final disposition:** Deferred.

### 2. `aaf08e61` — Transitionally accept both non-expanded and expanded workblock discovery stamps

**Upstream change:** `InterfaceAnnounceHandler` first checks a discovery
stamp against the unexpanded workblock (the infohash itself,
`expand_rounds=0`) and, only if it is not valid there, against the 20-round
expanded workblock. The stamp value comes from whichever workblock it is
valid against. Announcers still stamp against the expanded workblock, so this
prepares receivers for announcers that will stop expanding.

**Rust applicability:** rns-rs only checked the expanded workblock, so it
would reject the unexpanded discovery stamps future upstream announcers send.

**Local handling and evidence:** `parse_interface_announce_with_identity`
checks the unexpanded workblock first, then the expanded one, and takes the
value from the one the stamp is valid against.
`discovery_stamps_against_either_workblock_are_accepted` accepts a stamp
ground against each workblock with the matching value and still rejects one
valid against neither. rns-rs announcers keep the expanded workblock, as
upstream's do.

**Final disposition:** Integrated.
