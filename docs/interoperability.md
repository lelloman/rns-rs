# Interoperability and Upstream Tracking

rns-rs is a port of the Python reference implementation of Reticulum, not a
clean-room design. A Rust node joins a network alongside Python nodes and
exchanges announces, establishes links, and transfers resources with them. The
wire protocol it implements is written down in the
[Protocol Specification](protocol-spec.md).

## How parity is maintained

The accepted upstream baseline is recorded in [UPSTREAM.md](../UPSTREAM.md):
the Reticulum version, the canonical commit, the `RNS` tree hash, and the
validation that ran when it was accepted. It is the single place the
baseline version is stated.

Every upstream commit since the previous baseline is audited individually and
given a disposition: ported, already covered, non-runtime, or deferred with a
reason. The records live in [docs/upstream-parity/](upstream-parity/README.md):

- `reticulum-X.Y.Z-audit.md` is the commit-by-commit working record.
- `reticulum-X.Y.Z-parity.md` is the concise acceptance record written when
  the baseline is promoted.
- `-rgit` and `-rgit-N` suffixes mark advancements of the development tip that
  did not change the upstream version number.

Old audits are never rewritten. The daily operator report
(`scripts/vps_daily_report.py`) checks the upstream repository for drift and
opens a new `reticulum-next-audit.md` when commits appear. The full workflow
and per-commit integration rules are in the
[parity README](upstream-parity/README.md).

## What is verified

| Check | What it proves | Where |
|-------|----------------|-------|
| Conformance vectors | Byte-exact agreement with Python on packet encoding, hashing, encryption, announces, links, and resources | `tests/fixtures/`, generated by `tests/generate_vectors.py` from a pinned Reticulum 1.4.0 checkout |
| Live Python/Rust interop | A Rust node and a Python node exchange announces, links, and resources in-process | `cargo test -p rns-net --test python_interop`; CI runs it against Reticulum 1.4.2, 1.5.4, 1.5.5, 1.6.0 (the signed release commit `cb126089`) and 1.6.1 (the signed release commit `cff4d03f`) from the GitHub mirror; rgit tips past a release are verified manually from a local checkout, see the parity records |
| Utility interop | Rust CLI tools against Python tools and vice versa | `cargo test -p rns-cli --test utility_interop -- --ignored` |
| Docker end-to-end matrix | Multi-node behaviour across chain, mesh, and star topologies, plus NAT traversal, supervision, reconnection, and `rntun` | `tests/docker/`, see [Development](development.md#docker-end-to-end-suites) |
| Live backbone smoke | Reachability through the public backbone from two VPS entry points | [Manual Backbone Smoke Test](manual-backbone-smoke.md), run daily |

The conformance vectors keep their historical 1.4.0 provenance deliberately:
the formats they pin have not changed, and regenerating them against each new
upstream would lose the ability to detect an accidental upstream break. The
parity records state exactly which checks were rerun for each advancement and
which were inherited. Physical radio hardware validation remains unclaimed.

## Scope of compatibility

- **Protocol**: full `RNS-Compat/1` as specified, including IFAC, ratchets,
  link MTU discovery, resources with compression, and the Backbone interface
  with discovery.
- **Configuration**: Python config files parse unchanged, including
  ingress-control keys. rns-rs adds keys of its own, listed in
  [Configuration](configuration.md).
- **State**: identities and retained-ratchet files are file-compatible with
  Python, with the caveats in [Local Ratchets](local-ratchets.md#storage).
- **Tools**: `rnsd`, `rnstatus`, `rnpath`, `rnprobe`, `rnid`, `rnsh`, `rncp`,
  `rnx`, `rnir`, `rnpkg` and `rnodeconf` mirror their Python namesakes; see
  the [surface record](upstream-parity/reticulum-1.6.0-surface-parity.md)
  for what still differs.
- **Extensions**: [Hooks](hooks.md) and [Direct Link](direct-link.md) are
  additive. A Python peer never sees hooks. Direct Link asks a link peer
  whether it implements it with a link packet in context `0x80`, which
  upstream drops without a reply or proof; a peer that stays silent is sent
  no further Direct Link traffic, and its link and channel are left alone.
  `cargo test -p rns-net --test direct_link_python_interop -- --ignored`
  checks this against a Python peer with and without a channel.

## Unresponsive path recovery

A path is marked unresponsive when a link through it is never
established, and an announce may then replace it where it otherwise would
not. Upstream (Transport.py at `cff4d03f`) decides on its single path per
destination: an announce it has already heard (the same emission time)
replaces an unresponsive path when it arrives over more hops, through
whatever next hop, and since `8c73e203` that replacement updates the path
table without being rebroadcast.

rns-rs's own rules, the default (`unresponsive_path_recovery = native`),
differ:

- An already-heard announce through a next hop other than the path's is
  rejected, so an unresponsive path is not recovered through a neighbour
  that relays the same announce. This is the main difference.
- It is also taken over the same or fewer hops, which upstream does not.
- It is also taken for an expired path, where upstream takes only an
  announce it has not heard.
- "The same emission time" is the newest of the path's random blobs, where
  upstream scans them in order and stops at the first that reaches the
  announce's.

In both modes a replacement accepted only because the path is unresponsive
is not rebroadcast.

The native rules also differ from upstream for paths that are not
unresponsive, because rns-rs keeps announces through another next hop as
alternative paths:

- A newer announce through another next hop is added as an alternative
  path. With one path per destination it is kept only when it ranks first
  (no more hops than the path), so a newer announce over more hops through
  another neighbour leaves the path as it was (it is still rebroadcast);
  upstream takes it.
- An announce through another next hop emitted before the path's newest
  random blob is rejected, even for an expired path, where upstream takes
  any announce it has not heard.

`unresponsive_path_recovery = upstream` decides every path update as
upstream does, against the destination's primary path, and an accepted
announce replaces that path whatever its next hop, keeping the replaced
path's random blobs. Both keep this implementation's distrust of emission
times implausibly far in the future (`MAX_EMISSION_TIME_SKEW_SECS` in
`rns-core/src/transport/pathfinder.rs`).

The rns-rs-only path options combine with it as follows:

- `max_paths_per_destination` above 1: under `upstream` announces only
  replace the primary path, as upstream keeps one path, so they add no
  alternatives, and announces that could not update the primary path are
  prefiltered as upstream prefilters them. Paths already stored beside it
  stay. Under `native`, marking a path unresponsive promotes an
  alternative when the destination has one.
- `prefer_shorter_path`: a strictly shorter announce is still taken, in
  either mode, by rns-rs's own rules, and is rebroadcast. Upstream has no
  such option, so with it set `upstream` differs from upstream for these
  announces.

## Performance claims

rns-rs prioritises reliability, correctness, security, traffic management,
and practical performance across constrained and fast links. Upstream's Python
throughput figures describe that implementation and its environment; they are
not measurements of this port.

Any native performance claim should state the hardware, build profile, enabled
features, workload, network conditions, and measurement method. Routing-only
microbenchmarks and end-to-end application throughput measure different work,
and comparisons need equivalent behaviour and settings alongside correctness
and interoperability validation. The [benchmark runner](../bench/README.md)
and the findings documents next to it are the project's own measurements.
