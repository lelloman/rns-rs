# Interoperability and Upstream Tracking

rns-rs is a port of the Python reference implementation of Reticulum, not a
clean-room design. A Rust node joins a network alongside Python nodes and
exchanges announces, establishes links, and transfers resources with them. The
wire protocol it implements is written down in the
[Protocol Specification](protocol-spec.md).

## How parity is maintained

The accepted upstream baseline is recorded in [UPSTREAM.md](../UPSTREAM.md):
the Reticulum version, the canonical commit, the `RNS` tree hash, and the
validation that ran when it was accepted. At the time of writing that is
Reticulum 1.5.7 at the rgit tip of 2026-10-05.

Every upstream commit since the previous baseline is audited individually and
given a disposition: ported, already covered, non-runtime, or deferred with a
reason. The records live in [docs/upstream-parity/](upstream-parity/README.md):

- `reticulum-X.Y.Z-audit.md` is the commit-by-commit working record.
- `reticulum-X.Y.Z-parity.md` is the concise acceptance record written when
  the baseline is promoted.
- `-rgit` and `-rgit-N` suffixes mark advancements of the development tip that
  did not change the upstream version number.

Old audits are never rewritten. The daily operator report
(`scripts/vps_daily_report.py`) checks the upstream repository for drift and
opens a new `reticulum-next-audit.md` when commits appear. The full workflow
and per-commit integration rules are in the
[parity README](upstream-parity/README.md).

## What is verified

| Check | What it proves | Where |
|-------|----------------|-------|
| Conformance vectors | Byte-exact agreement with Python on packet encoding, hashing, encryption, announces, links, and resources | `tests/fixtures/`, generated by `tests/generate_vectors.py` from a pinned Reticulum 1.4.0 checkout |
| Live Python/Rust interop | A Rust node and a Python node exchange announces, links, and resources in-process | `cargo test -p rns-net --test python_interop`; CI runs it against Reticulum 1.4.2, 1.5.4, and 1.5.5 from the GitHub mirror; 1.6.0 exists only on the normative rgit repository so far and is verified manually from a local checkout, see the parity records |
| Utility interop | Rust CLI tools against Python tools and vice versa | `cargo test -p rns-cli --test utility_interop -- --ignored` |
| Docker end-to-end matrix | Multi-node behaviour across chain, mesh, and star topologies, plus NAT traversal, supervision, reconnection, and `rntun` | `tests/docker/`, see [Development](development.md#docker-end-to-end-suites) |
| Live backbone smoke | Reachability through the public backbone from two VPS entry points | [Manual Backbone Smoke Test](manual-backbone-smoke.md), run daily |

The conformance vectors keep their historical 1.4.0 provenance deliberately:
the formats they pin have not changed, and regenerating them against each new
upstream would lose the ability to detect an accidental upstream break. The
parity records state exactly which checks were rerun for each advancement and
which were inherited. Physical radio hardware validation remains unclaimed.

## Scope of compatibility

- **Protocol**: full `RNS-Compat/1` as specified, including IFAC, ratchets,
  link MTU discovery, resources with compression, and the Backbone interface
  with discovery.
- **Configuration**: Python config files parse unchanged, including
  ingress-control keys. rns-rs adds keys of its own, listed in
  [Configuration](configuration.md).
- **State**: identities and retained-ratchet files are file-compatible with
  Python, with the caveats in [Local Ratchets](local-ratchets.md#storage).
- **Tools**: `rnsd`, `rnstatus`, `rnpath`, `rnprobe`, `rnid`, `rnsh`, `rncp`,
  and `rnx` mirror their Python namesakes in role and most flags.
- **Extensions**: [Hooks](hooks.md) and [Direct Link](direct-link.md) are
  additive. A Python peer never sees them.

## Performance claims

rns-rs prioritises reliability, correctness, security, traffic management,
and practical performance across constrained and fast links. Upstream's Python
throughput figures describe that implementation and its environment; they are
not measurements of this port.

Any native performance claim should state the hardware, build profile, enabled
features, workload, network conditions, and measurement method. Routing-only
microbenchmarks and end-to-end application throughput measure different work,
and comparisons need equivalent behaviour and settings alongside correctness
and interoperability validation. The [benchmark runner](../bench/README.md)
and the findings documents next to it are the project's own measurements.
